# Implementation Plan

## 1. 目录收敛

- [x] 1.1 为网关模型目录加入按上游归属的过滤能力 (P)
  - 目录拉取解析后、写入快照前，依据允许的归属集合过滤条目
  - 未提供集合时不过滤，保证既有部署行为逐字节不变
  - 归属比对忽略大小写与首尾空白
  - 完成条件：同一份目录数据，传与不传集合两种情形下的快照条目数可被断言区分
  - _Requirements: 2.1, 2.3, 2.4_
  - _Boundary: 网关模型目录_

- [x] 1.2 记录收敛结果，使白名单是否过窄可判断
  - 每次目录刷新后记录保留数与滤除数
  - 全部被滤除时同样记录，不静默出现空清单
  - 完成条件：以注入的日志器可断言两个数字均被记录
  - _Requirements: 2.5_
  - _Depends: 1.1_

- [x] 1.3 解析白名单配置并提供内置缺省
  - 从环境变量读取逗号分隔的归属列表
  - 未配置或值全为空白时回落到内置缺省，而非解释为「全部滤除」
  - 内置缺省须排除条目数最多且与他者大量重复的那个聚合型上游
  - 完成条件：未配置、空白、多项三种输入各有对应断言
  - _Requirements: 2.2_
  - _Boundary: 网关配置解析_

- [x] 1.4 在服务装配处把白名单透传给目录组件
  - 装配时将配置解析所得传入目录组件
  - 未启用网关套件时不产生任何相关注册
  - 完成条件：启用与未启用两条路径均可跑通既有测试
  - _Requirements: 1.4, 2.1_
  - _Depends: 1.1, 1.3_

- [x] 1.5 补齐收敛能力的单元测试
  - 覆盖不过滤、命中过滤、大小写与空白容错、空集全滤四种情形
  - 覆盖配置解析的未配置/空白/多项三种输入
  - 完成条件：测试全绿，且移除过滤逻辑会导致对应用例失败
  - _Requirements: 2.1, 2.2, 2.3, 2.5_
  - _Depends: 1.3_

## Implementation Notes

### 端到端证据（任务 3.1，2026-07-29）

以**真实组件**跑通，且对话所用 model id **取自合并结果**而非手敲常量：

```
① resolveAiGatewayConfig → baseUrl=…/pi-labs/compat  白名单=anthropic,openai,google-ai-studio
② GatewayModelCatalog 真实拉取 CF → filtered {kept:470, dropped:1995}
③ mergeModelCatalog → 471 条（470 网关 + 1 自配；自配未被吞并）
④ [anthropic] anthropic/claude-opus-5 → HTTP 200  1.9s  回复 "ok"
④ [openai]    openai/gpt-5.5          → HTTP 200  1.5s  回复 "ok"
```

### 任务 3.2 结论：无需改动

「零代码适配层」成立 —— 未对 `ai-gateway` 的认证、路径、转发做任何改动即跑通。
本 spec 的代码改动仅为**目录收敛**与**可诊断性**两项，皆为新增能力而非适配。

### 端到端揪出的一个真实局限

首次运行挑中 `openai/gpt-4-turbo:batch` → 401。那是批处理 API 变体，需另一套凭据。
provider 级白名单**收不掉**（`owned_by` 同为 openai）。已写入 design 的 Risks、
research 的局限节与用户文档第六节，本期有意不处理（判定可对话性需能力元数据，
而 CF 目录只给 id/owned_by/cost，id 模式匹配属脆弱启发式）。

### 顺带修的既有测试

`config.test.ts` 的「最小合法配置」用 `toEqual` 精确比对配置对象，新增
`providerAllowlist` 字段后失败。已更新期望（非放宽断言 —— 仍是精确比对）。

### 一个 flaky 观察

全量首跑时 `attachment-profile-disabled-subprocess.test.ts` 因 40s 超时失败，
单独跑 3/3 通过（17.7s），二次全量亦通过。属并发负载下的 flaky，与本 spec 无关
（该用例只 import rpc-channel/session，不触达 ai-gateway）。
