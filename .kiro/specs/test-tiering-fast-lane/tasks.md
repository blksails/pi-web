# Implementation Plan — test-tiering-fast-lane

> 排序理由（与 design.md 的 Migration Strategy 一致，但**顺序有一处刻意调整**）：
> 设计初稿把「改配置」排在「重命名」之前，那会让仓库在两步之间处于全部文件涌入 fast 档的破碎状态。
> 实际上**重命名可以先做且零破坏** —— `foo.it.test.ts` 仍匹配现有 include 模式 `test/**/*.test.ts`，
> 旧配置继续正常工作。故改为：守卫先建（此时应大面积报红，那是它有判别力的证明）→ 重命名（守卫转绿）
> → 再切配置。全程无破碎窗口。

    记录文件数/用例数/跳过数/耗时；核对每次的 `passed + failed + skipped == 总数`
    （vitest 的 worker 崩溃会被算成「0 failed」，只看红绿会漏）
  - 用可复跑的脚本产出 fast / it / e2e 三档的确定性文件清单，判据取自 design.md：
    真实 spawn/fork ∪ `mkdtemp` ∪ pi SDK 值导入 ∪ `test/integration/` ∪ 整文件被外部凭据门控

  - **观察完成**：三份清单文件数为 198 / 75 / 3，合计 276，与 `find test -name '*.test.ts'` 的总数逐位相等
  - _Requirements: 1.1, 7.2_

## 2. 守卫层

## Implementation Notes

### 与计划的偏离(均已实测验证)

1. **2.1 先于 1.1 执行**。计划把「生成归位清单」排在「实现判据」之前,那会让两处各编码一份
   分档判据,直接违反 design 的「tier-rules 是单一事实来源」。改为先实现判据,再由
   `scripts/classify-tiers.mjs` 经 jiti 复用它产出清单。

2. **fast 档拆成两次 vitest 调用而非一次**。design 写的是「两个快档并行(一次调用)」,
   实测发现 `--no-isolate` 是**全局**开关、不分 project,合并调用会打坏 fast-mock 的 `vi.mock`。
   改为两次调用 + **并发执行**(fast-mock 输出缓冲后补打,避免摘要交错),墙钟 6.25s。

3. **判据新增「剥注释」步骤**。design 未提。dogfood 时发现判据自身的单测文件被自己的
   文档注释打中(注释里写了 `from "node:child_process"` 与 `vi.mock(`)。这与早期手工 grep
   的 4 个误报是同一类问题,故在判据里补 `stripComments`(保留换行以维持行号)。

4. **判据新增 `RUNTIME_DETECTED_IT` 名册**。静态直接导入分析**原理上**看不见
   「测试 → src 模块 → 起子进程」,而传递分析 59% 误报不可用。由运行期哨兵扫描
   204 个 fast 候选时暴露 16 个文件 / 51 个用例,固化为名册。

5. **重命名撞车处理**。`ext.e2e` 与 `ext.integration` 剥掉 infix 后同名(http / session /
   pi-rpc-process 同理)。规则:同组撞车时**双方都保留原 infix**(与处理顺序无关,确定性)。

### 实测教训(值得记住的坑)

- ★ **`isolate` 与 `fileParallelism` 一样,project 级被 vitest 2.1.9 忽略**。
  配置里写 `isolate: false` 无效(12.34s,prepare 12.85s),CLI `--no-isolate` 才生效
  (4.03s,prepare 1.16s)。`poolOptions.threads.isolate` 同样无效(15.74s)。这是同族坑的**第二次**。
- ★ **`vitest.workspace.ts` 存在时,`-c <config>` 的根级 `test.setupFiles` 被完全忽略**。
  哨兵因此 0 次加载,而结果显示「零违规」—— 没装上的哨兵报出的绿,和真的没有违规长得一样。
  **本 spec 被这个坑骗过两次**,两次都写进了文档才被后续实测推翻。
- ★ **改写 `child_process` 命名空间拦不住 ESM 具名导入**(`import { spawn } from ...`,实测
  `nsWorked === false`),而 `src/rpc-channel/pi-rpc-process.ts` 正是这么写的。
  `diagnostics_channel("child_process")` 则只在**异步** spawn 时发布,`spawnSync`/`execFileSync`
  完全不发。最终用**模块别名**(导入不报错、调用才报错),是唯一覆盖「任意导入写法 × 同步异步」的手段。
- ★ **归位时撞见两个会静默丢测的文件**:`extensions-schema.e2e.test.ts` 与
  `self-resolved-builtins.e2e.test.ts` 判定是 fast,却因历史命名带着 `.e2e` —— 新规则下
  会被默认路径跳过。守卫为此专设一条「e2e 必须在名册里」的断言。
