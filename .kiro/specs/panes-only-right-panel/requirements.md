# Requirements Document

## Project Description (Input)
**谁有问题**:pi-web 的宿主与所有 agent 作者。

**现状**:右侧面板存在两套互不相通的机制 —— 旧的 `slots.panelRight`(agent 交宿主 realm 的
React 节点,同 realm 渲染)与新的 pane 声明键(宿主实例化 PanesHost,每个 pane 跑在独立的
opaque-origin iframe)。两套并存导致能力面分叉:旧槽拿得到宿主 realm 的一切,pane 只拿得到
协议明确搬运的部分;并因此迫使 `host-builtin-panes` 规定「声明旧槽的 agent,内置 panes 整体
让位」——只要还有一个 agent 用旧槽,内置 pane 在那个 agent 下就永远不存在。旧槽同时是绕过
既有 pane 隔离边界的口子。实测仓内有 9 个 `panelRight` 声明者。

**该变成什么**:右侧面板收敛为唯一的 pane 机制。9 个声明者全部重写为 iframe guest,
为此先补齐协议缺口(共享状态 KV 跨 realm 通道、宿主信号内置化)并新建 guest 侧 canvas 插件
车道;处置槽车道的测试夹具;最终从 web-kit/protocol **删除** `panelRight` 类型,并留下
「零声明者」的机械守卫。迁移是**等价改写**:每个示例既有 e2e 断言的语义必须仍被守住,
载体可换、保护面不可缩。

详见 `.kiro/specs/panes-only-right-panel/brief.md`(含 9 个声明者的分类盘点、两处协议缺口、
canvas 包装层的两处真逻辑,均为实测)。

## Introduction

本特性把右侧面板从「两套并存的机制」收敛为「唯一的 pane 机制」,并删除已废弃的那一套。

它不是一次改名。旧槽收的是**宿主同 realm 的渲染物**,pane 是**隔离环境里的独立文档** ——
凡是伸手进宿主 realm 的面板逻辑都必须改写成经受管通道说话的 guest。因此本特性的主体是
**能力补齐 + 逐个重写 + 最终删除**,而不是「切换一个开关」。

收敛带来的直接收益有三:内置 pane 对**所有** agent 生效(不再有「让位」这种例外形态);
第三方面板代码不再与宿主同权;同一件事不再因为走了哪条路径而能力不同。

### 两处由本文档定夺的决策(brief 中标为待定,按自主档授权在此确定)

1. **对话流内元素点击 → 面板聚焦**这类交互(现由某示例在宿主环境上挂全局监听实现):
   定为**宿主提供的领域中立事件**,而非各 agent 自行在宿主环境里挂监听。理由是会话外壳是
   领域中立层(既有守卫会拒绝其中出现领域词汇),让每个 agent 往那里挂监听既不可持续、
   在隔离形态下也做不到。
2. **槽车道的测试夹具**(现用右侧面板槽守护「多槽渲染」与「运行时扩展签名校验」):定为
   **改用其余保留槽承载**,不随本特性废弃。理由是右侧面板槽只是保留槽之一,其余槽不在本
   特性范围内;夹具守护的是槽机制与签名校验本身,与面板形态无关。

### 一处由勘察修正的预判

`surface` 相关的读快照 / 订阅 / 执行命令 / 探测命令可用性,pane 的既有通道**已全部具备**,
故依赖这些能力的面板迁移**不需要新增协议**。真正缺的只有可写回的共享状态(见 Requirement 2)。

## Boundary Context

- **In scope**:右侧面板槽的废弃与删除;全部现存声明者的重写;为重写所必需的能力补齐
  (共享状态的跨隔离边界访问、宿主环境信息与交互事件的统一供给、隔离环境内的面板插件);
  槽车道夹具的改挂;`host-builtin-panes` 中「旧槽让位」规则的作废与相应断言清理;
  零残留的机械守卫。
- **Out of scope**:其余保留槽的废弃(本特性只废右侧面板槽);面板内容的功能增强或重设计
  (迁移是等价改写);pane 访问宿主文件系统的能力(属 `pane-host-capabilities`);
  新增内置 pane(属 `builtin-pane-suite`);pane 隔离模型本身的修改(属 `isolated-panes`)。
- **Adjacent expectations**:本特性**依赖** `host-builtin-panes` 已交付的 pane 声明键、
  来源合并与宿主具名信号;**依赖** `isolated-panes` 的授权模型与结构化错误语义。
  本特性**不拥有** agent 侧的工具与权限,也不拥有 pane 内部的具体 UI 实现。

## Requirements

### Requirement 1: 右侧面板的唯一机制

**Objective:** 作为 agent 作者,我希望右侧面板只有一种声明方式,以免同一件事在两条路径上
能力不同、也不必先搞清楚自己走的是哪条路径。

#### Acceptance Criteria

1. Where agent 声明了 pane 定义, the 宿主 shall 在右侧面板渲染这些 pane,每个 pane 运行在
   与第三方 pane 同构的隔离环境中。
2. The 宿主 shall 不再提供任何形式的右侧面板槽,即不存在「交一个宿主同 realm 的渲染物作为
   右侧面板」这一途径。
3. When 宿主存在内置 pane, the 宿主 shall 对**所有** agent 渲染它们 —— 不存在任何使内置
   pane 整体不出现的 agent 声明形态。
4. The 代码库 shall 不含右侧面板槽键的任何声明、类型定义或引用,且该性质可被机械核验
   (不依赖人工通读)。
5. If 某处仍以右侧面板槽键进行判定或渲染, then 机械核验 shall 判定为不通过并指出位置。

### Requirement 2: 共享状态的跨隔离边界访问

**Objective:** 作为 agent 作者,我希望面板内容能读、订阅并写回会话级共享状态,以便在隔离
环境中仍能实现「人机共驾」——人在面板上的操作与 agent 工具读写同一份状态。

> 该能力是现存声明者中至少一个的迁移前置条件:既有的单向具名信号无法替代它,因为信号是
> 单向、只保留最新值、且无写回途径。

#### Acceptance Criteria

1. Where pane 被授予共享状态能力, the 宿主 shall 允许该 pane 读取被授权键的当前值。
2. Where pane 被授予共享状态能力, the 宿主 shall 允许该 pane 订阅被授权键,并在该键的值发生
   变化时通知它。
3. Where pane 被授予共享状态写入能力, the 宿主 shall 允许该 pane 写回被授权键;写回完成后,
   agent 侧下一次读取该键 shall 得到新值。
4. When 某个键的值被任一方改变, the 宿主 shall 使所有订阅了该键的在世 pane 与宿主侧订阅者
   观察到同一个值(不存在一方更新而另一方停留在旧值)。
5. If pane 未被授予该能力, then 宿主 shall 拒绝其读、订阅与写入请求。
6. If pane 请求的键不在其授权范围内, then 宿主 shall 拒绝该请求,且拒绝结果不泄露该键是否
   存在。
7. The 宿主 shall 仅依据已装载的 pane 定义授予该能力 —— pane 自报的任何标识(含保留前缀)
   不产生任何权限。
8. If 该能力的请求或响应超出既有载荷上限, then 宿主 shall 按既有的超限语义拒绝,不另立一套。

### Requirement 3: 宿主环境信息与交互事件的统一供给

**Objective:** 作为 agent 作者,我希望主题明暗、以及「对话流内元素被点击」这类**宿主侧**的
环境信息与交互事件由宿主统一供给,而不必自己在宿主环境里挂监听 —— 后者在隔离形态下做不到,
在会话外壳这一领域中立层里也不被允许。

#### Acceptance Criteria

1. The 宿主 shall 向所有 pane 提供当前主题明暗状态,agent 无需自行计算。
2. When 宿主主题在明暗之间切换, the 宿主 shall 使所有在世 pane 观察到新状态。
3. When 对话流中的某个可聚焦元素被用户点击, the 宿主 shall 以领域中立的形式通知 pane,
   通知内容足以让 pane 识别被点击的对象。
4. The 宿主提供的这些信息 shall 以领域中立的名义供给,不含任何特定 agent 领域的词汇。
5. Where agent 未使用这些信息, the 宿主 shall 照常渲染其 pane,不产生错误。
6. The 宿主 shall 不因供给这些信息而向 pane 泄露宿主环境的可直接操作句柄。

### Requirement 4: 隔离环境内的面板插件

**Objective:** 作为 agent 作者,我希望自己为某个面板贡献的插件(附加图层、工具、检视器)
在该面板迁入隔离环境后仍然可用,以免迁移导致既有扩展点整体失效。

#### Acceptance Criteria

1. Where agent 声明了面板插件, the 宿主 shall 使这些插件在其目标 pane 的隔离环境内生效。
2. When 插件贡献了可见元素, the 该元素 shall 在 pane 内呈现并可交互,行为与迁移前一致。
3. If 某个插件在装载时不合法, then 宿主 shall 淘汰该插件并记录可定位的诊断,同时该 pane 的
   其余部分与其他插件 shall 仍然可用。
4. The 插件 shall 不因位于隔离环境内而获得超出其所在 pane 的授权。
5. Where agent 未声明任何面板插件, the 该 pane shall 正常工作(插件是可选扩展点,不是前置)。

### Requirement 5: 迁移的等价性

**Objective:** 作为宿主维护者,我希望每个被重写的面板在迁移后行为不回退,以免这次收敛以
「悄悄少了几个功能」为代价。

#### Acceptance Criteria

1. When 某个面板从旧机制迁到 pane, the 该面板既有的用户可观察行为 shall 保持不变。
2. The 迁移 shall 不减少既有验收断言所保护的行为面 —— 断言的载体可以改变,但每一条断言原本
   守护的行为必须仍被某条断言守护。
3. If 某条既有断言因本特性的契约变更而不再成立, then 该断言 shall 被改写为反映新契约且保护面
   不缩小的形式,而不是删除。
4. Where 某项行为依赖跨隔离边界的协作(例如一轮结束后的自动同步), the 验收 shall 包含一条
   独立断言直接检查该行为的结果 —— 仅检查元素数量或渲染成功不构成覆盖。
5. When 全部迁移完成, the 既有的面板相关端到端验收 shall 全部通过。
6. The 验收 shall 区分本特性引入的失败与既有的存量失败,存量失败不得被计为本特性的回归,
   也不得成为放宽验收标准的理由。

### Requirement 6: 其余槽机制不受影响

**Objective:** 作为宿主维护者,我希望本次只废右侧面板槽,不波及其余保留槽与运行时扩展的
安全校验。

#### Acceptance Criteria

1. The 本特性 shall 不改变除右侧面板槽以外的任何保留槽的可用性与语义。
2. When 一个扩展声明了多个保留槽, the 宿主 shall 照常渲染其余槽。
3. The 运行时代码扩展的签名校验行为 shall 仍被验收守护,包括签名无效与内容被篡改两种拒绝情形。
4. Where 某个验收夹具原先以右侧面板槽承载, the 该夹具 shall 改由其余保留槽承载并继续守护
   其原本的保护面。

### Requirement 7: 迁移过程的可诊断性与收尾

**Objective:** 作为 agent 作者,我希望在迁移窗口内能明确知道自己该改什么;作为宿主维护者,
我希望收尾时能机械地确认「真的没有残留」。

#### Acceptance Criteria

1. While 右侧面板槽尚未删除, when agent 仍以旧形态声明右侧面板, the 宿主 shall 输出指明
   迁移途径的诊断,且该诊断可定位到具体扩展。
2. When 右侧面板槽被删除, the 与该槽相关的过渡期诊断与让位规则的断言 shall 一并移除 ——
   不留下永不触发的死代码与死断言。
3. The 删除 shall 以「不存在任何声明者」为前置判据,且该判据由机械核验得出而非人工确认。
4. If 机械核验发现残留, then 删除 shall 不被执行,并报出残留位置。
5. When 全部工作完成, the 核验 shall 在一次运行中同时给出:类型检查结果、各测试面的结果、
   以及面板相关端到端验收的结果。
